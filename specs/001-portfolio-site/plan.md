# Implementation Plan: Personal Portfolio Site

**Branch**: `001-portfolio-site` (work currently on `restructure`) | **Date**: 2026-10-05 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/001-portfolio-site/spec.md`

## Summary

Rebuild the portfolio as a statically generated site with four top-level pages (Landing, About,
Projects, Fun) plus optional project detail pages. The site should be editorial in look, mobile
first, and work fully without JavaScript.

**Astro 7** generates plain HTML at build time. That gives every page the shared layout,
navigation, contact links, theme toggle and sharing tags without copying them (FR-030), while
shipping no JavaScript to content pages (FR-027). Projects and Fun-page interests are Markdown
files whose frontmatter the build validates against typed schemas (FR-009, FR-020, FR-032, FR-033).

**Svelte 5** is used only for the Fun page's interactive math pieces and the site-wide easter
eggs. Pieces load when they scroll into view; easter eggs load only when someone triggers one. The
landing-hero motion is a curve computed at build time, shipped as inline SVG and animated with CSS
only.

Build output goes to `dist/` (Astro's default), the published directory under constitution
v1.3.0. **No existing file is deleted or moved**: the hand-written `site/` stays in the repository
as a frozen, unpublished record. The existing `pages.yml` workflow gains a build step, uploads
`dist/` instead of `site/`, and remains the single deploy path.

## Technical Context

**Language/Version**: TypeScript 5.x (Astro and Svelte components; pure logic modules in
`src/lib/`), HTML and CSS. Node.js 24 LTS for development and CI (Astro 7 requires ≥ 22.12.0).

**Primary Dependencies**: `astro` 7.x (static output, content collections, `astro:assets`, Fonts
API), `@astrojs/svelte` 9.x, `svelte` 5.x, and `sharp` for image conversion (Astro's default image
service). Dev only: `vitest` 5.x and `@astrojs/check`. Each is justified in
[research.md](./research.md) R3 and R13.

**Storage**: Files only. Markdown and YAML content under `src/content/` and `src/data/`, plus
static assets under `public/`. The visitor's theme choice lives in the browser's `localStorage`,
with every access wrapped in try/catch.

**Testing**: Vitest unit tests for non-trivial logic in `src/lib/` (Fourier transform, curve
generation, theme resolution, content checks). Content schemas are enforced at build time by
Astro's Zod 4 validation. The CI pull-request workflow runs Lighthouse CI budgets and a lychee
link check. Spec scenarios that need a human (no-JS, viewports, theme persistence) are covered in
[quickstart.md](./quickstart.md).

**Target Platform**: Static site on GitHub Pages at `https://athenafung1.github.io` (root path,
no base prefix). Browser support is the current and prior major versions of Chrome, Firefox,
Safari and Edge, on both desktop and mobile (iOS Safari and Android Chrome are first-class).

**Project Type**: Static website (single project, generated at build time).

**Performance Goals**: Under 1 MB transferred per page; LCP under 2.5 s on Lighthouse mobile
throttling; Lighthouse Performance and Accessibility ≥ 90 per page; interactive pieces hold
60 fps on a mid-range phone and pause when off screen or in a background tab; zero layout shift
from web fonts (fallback font metrics generated by the Fonts API).

**Constraints**: Mobile first, designed at 320px and enhanced upward through 768px and 1280px,
with no horizontal scroll. Touch targets at least 44×44 CSS px. No JavaScript is needed for
content, navigation or contact. No third-party scripts, embeds or trackers. At most two font
families, self-hosted. Respects `prefers-reduced-motion`. No phone number or street address
anywhere (FR-036).

**Scale/Scope**: 4 top-level pages, 1–20 project cards, about 2–4 project detail pages, about
5–12 interest entries, 1 interactive piece at launch (more later), 1–3 easter eggs, and 2 legacy
redirect stubs. One author, who is the only maintainer.

**Structure Decision**: a single Astro project at the repository root. Svelte is confined to
`src/islands/`, and all non-trivial logic lives in framework-free `src/lib/` so it can be
unit-tested without a browser and reused between build-time Astro code (fallback SVGs, hero
curve) and runtime Svelte islands. `site/`, `archive/` and `.specify/` are untouched and are
never part of the build. No existing file in the repository is deleted or moved.

## Complexity Tracking

| Violation (Principle V) | Why Needed | Simpler Alternative Rejected Because |
|---|---|---|
| Build step and framework (Astro) | FR-030 (shared layout and navigation without per-page copying) and FR-027 (navigation without JS) can't both be met by hand-written HTML. Astro also enforces content rules at build time (FR-009, FR-033, FR-036) and generates AVIF/WebP images with dimensions (Principle IV), replacing far more than 50 lines of custom code. | Plain HTML needs copied nav/footer (breaks FR-030) or JS-injected nav (breaks FR-027). Eleventy was the earlier recommendation and is simpler, but the author chose Astro so the static pages and the Svelte islands share one component model and one toolchain. Eleventy plus Svelte islands would need a hand-built Vite pipeline. |
| UI component library for islands (Svelte 5) | The interactive pieces carry real UI state: freehand pointer drawing, a term-count slider, preset selection, play/pause and reset, all kept in sync with a canvas. Svelte's compiled reactivity keeps this small, and its runtime is loaded only on the Fun page or when an easter egg is triggered (size measured against the R10 budget). | Vanilla JS could build one piece, but the author plans to add more over time, and hand-wiring state to DOM for each piece is the larger long-term cost. Svelte stays confined to `src/islands/`. Content pages ship zero Svelte. |
| `sharp` (image processing) | Required by `astro:assets` to emit AVIF/WebP at multiple widths (Principle IV). | Converting and resizing every image by hand is error-prone and breaks the "author edits plain content" workflow. |
| Dev tooling (`vitest`, `@astrojs/check`) | Constitution requires unit tests for non-trivial JS. Vitest shares Astro's Vite config, so TypeScript and import aliases work unchanged. `astro check` type-checks `.astro` and `.svelte` files. | `node:test` has no dependency but would need separate TypeScript handling and import-specifier rules that differ from the app code. Both tools are dev-only and never shipped. |
